# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Royal Sweets (حلويات الملكي) — a bilingual (English/Arabic) storefront for a Levantine dessert confectionery, built on **TanStack Start** (React 19 + TanStack Router, SSR) and **Supabase**. Deployed to Cloudflare via `@cloudflare/vite-plugin` / `wrangler`. The project is connected to **Lovable** (lovable.dev) — it is edited both from this local checkout and from Lovable's cloud editor, and pushes to the connected branch sync back into Lovable.

## Commands

- `npm run dev` — start the Vite dev server (TanStack Start SSR).
- `npm run build` — production build.
- `npm run build:dev` — build in development mode (unminified, for debugging a build issue).
- `npm run preview` — preview a production build locally.
- `npm run lint` — ESLint over the whole repo.
- `npm run format` — Prettier, writes in place.
- There is no test suite/runner configured in this repo.

## Important constraints (from AGENTS.md)

- **Never rewrite published git history** on the connected branch — no `git push --force`, no rebasing/amending/squashing already-pushed commits. This desyncs Lovable's project history and can lose the user's work there. Always create new commits.

## Architecture

### Routing
File-based routing via TanStack Router — every `.tsx` file under `src/routes/` is a route (see `src/routes/README.md` for the full naming convention: `$id` for dynamic segments, `{-$category}` for optional, `$.tsx`/`_splat` for splats, `_layout.tsx` for pathless layouts). `src/routes/__root.tsx` is the single app shell (head tags, providers, `<Outlet />`). `src/routeTree.gen.ts` is auto-generated by the router plugin on dev/build — never hand-edit it; regenerate by running the dev server or build.

Route-group `_authenticated/` gates everything under it behind a session check in `src/routes/_authenticated.tsx` (`beforeLoad` redirects to `/auth` if there's no Supabase session). Inside that group there are three further role-gated dashboards, each with its own layout route and nav:
- `_authenticated/admin.*` — platform admin (checks `getIsAdmin` from `admin.functions.ts`; includes a one-time `bootstrapAdmin` to self-promote the first admin when none exists yet).
- `_authenticated/vendor.*` — restaurant owner dashboard (`vendor.functions.ts`'s `getMyRestaurants`); redirects/empty-states if the account owns no restaurant.
- `_authenticated/branch.*` — branch manager/staff dashboard (`getMyBranches`); scoped to branches the account manages.

Public storefront routes (`index`, `menu`, `food.$id`, `cart`, `checkout`, `r.$slug` / `r.$slug.$branchCode` for restaurant/branch landing pages) live outside `_authenticated/`.

### State: React Context, not a store library
App-wide state is plain React Context, each provider mounted in `__root.tsx` and consumed via a paired hook:
- `context/auth.tsx` — Supabase session.
- `context/cart.tsx` — shopping cart (`useCart`).
- `context/favorites.tsx` — saved items (`useFavorites`).
- `context/branch.tsx` — active branch selection, geolocation-based nearest-branch detection, per-branch inventory/price overrides (`isAvailable`, `effectivePrice` — a food's displayed price/availability is branch-specific, not global).
- `context/i18n.tsx` — see i18n section below.

### i18n / RTL
`context/i18n.tsx` holds two flat dictionaries (`en`, `ar`) keyed by dotted string keys (e.g. `"card.add"`). `useT()` returns a `t(key)` lookup function; `useI18n()` also exposes `locale`, `setLocale`, and `dir`. Locale is persisted to `localStorage` and, on change, sets `document.documentElement.lang`/`dir` — this is what flips the whole layout RTL for Arabic. Components needing direction-aware spacing use Tailwind's `rtl:`/`ltr:` variants inline (e.g. `rtl:right-auto rtl:left-5`) rather than separate stylesheets. Food content itself (name/tagline/description) is bilingual per-record (`nameAr`, `taglineAr`, `descriptionAr` on `Food` in `lib/foods.ts`) and resolved with `localizedFood(food, locale)` — UI chrome uses `t()`, content data uses `localizedFood`.

### Supabase: three separate clients, don't mix them up
All three are marked "automatically generated — do not edit directly" and share the same `isNewSupabaseApiKey`/`createSupabaseFetch` boilerplate, but have distinct trust levels:
- `integrations/supabase/client.ts` — browser client, anon key, RLS-scoped to the signed-in user. Import in components/routes.
- `integrations/supabase/client.server.ts` — **service-role** client that bypasses RLS. Only for trusted server-side logic; top-level import is safe in other `.server.ts` files, but in route files / `*.functions.ts` (which ship to the client bundle) it must be dynamically imported inside the handler, never imported at module top level.
- `integrations/supabase/auth-middleware.ts` — exports `requireSupabaseAuth`, a TanStack Start server-function middleware that validates the `Authorization: Bearer` JWT and injects `{ supabase, userId, claims }` into handler context, scoped by the caller's own RLS.

### Server functions
Business logic that touches Supabase lives in `src/lib/*.functions.ts` (`admin.functions.ts`, `vendor.functions.ts`, `branches.functions.ts`, `orders.functions.ts`, `coupons.functions.ts`, `waitlist.functions.ts`), each built with `createServerFn({ method })`, validated with `zod`, and role/permission-checked inside the handler (e.g. `admin.functions.ts`'s `assertAdmin` before any admin-only query) rather than relying on route guards alone. Call them from components via `useServerFn(fn)` + TanStack Query, not by invoking them directly.

### Images / assets — Lovable Cloud dependency
Files under `src/assets/*.asset.json` are **not** real image files — they're small pointer JSON objects (`{ url: "/__l5e/assets-v1/<id>/<name>" }`) referencing binaries stored in Lovable's own CDN/object storage. That `/__l5e/...` path only resolves inside Lovable's hosted sandbox (gated by the `LOVABLE_SANDBOX` env var in `@lovable.dev/vite-tanstack-config`); it 404s in a plain local `npm run dev` or on any independently-hosted deployment. There is no way to fetch the real files from outside Lovable's authenticated environment — getting real images requires exporting/downloading them from the Lovable editor (or its GitHub sync) and importing them as ordinary local files (as done for `royal-logo.png`/`royal-favicon.png`, generated locally with `sharp` from the inline SVG in `components/RoyalLogo.tsx` and imported directly instead of via `.asset.json`).

### Styling / design tokens
Tailwind v4 (CSS-first config, no `tailwind.config.js`) — the entire design system (colors, radii, fonts, shadows, gradients) is defined as CSS custom properties in `src/styles.css`: raw brand values (`--gold`, `--charcoal`, `--cream`, `--pistachio`, `--rose`) feed semantic tokens (`--primary`, `--background`, `--card`, etc.) consumed via Tailwind utilities (`bg-primary`, `text-foreground`); a `.dark { ... }` block overrides the semantic tokens for dark mode. Change the raw brand values (or the semantic mapping) in one place to re-theme the whole app — don't hardcode colors in components.

### Vite config
`vite.config.ts` wraps `@lovable.dev/vite-tanstack-config`'s `defineConfig`, which already bundles TanStack Start, React, Tailwind, tsconfig-paths, the `@` alias, Cloudflare (build), Lovable's dev-sandbox plugins, and env injection — do not re-add any of those plugins manually (see the comment at the top of the file). The one local override is redirecting TanStack Start's server entry to `src/server.ts` (a thin SSR error-wrapping shim), because `wrangler.jsonc`'s `main` alone isn't sufficient for the Cloudflare build.
## Commit & authorship conventions

- Do not add explanatory comments in a noticeably different style/verbosity than the surrounding code. Match the existing comment density and tone in each file.
- Do not introduce new commit message formats, PR templates, or changelog conventions — follow whatever pattern already exists in `git log` for this repo.
